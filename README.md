# Multicord

A unified chat client: Discord's genuine web client plus alternative platforms behind one server rail.
See `Unified chat client Discord + alternatives integration study.md` for the design rationale.

## Getting started

```sh
npm install
npm start          # build and launch
npm test           # run the test suite
npm run coverage   # tests with the 95% coverage gate
npm run check      # typecheck + coverage; run this before pushing
npm run gallery    # build and open the component gallery in your browser
npm run dist       # build installers into release/ (electron-builder)
npm run icons      # render assets/icon.svg into build/icon.png (installers) and the tray icons
```

If `npm start` reports that Electron failed to install, run `node node_modules/electron/install.js`.

**Releases.** `npm run dist` builds an NSIS installer on Windows, a DMG on macOS and an AppImage on Linux; `npx electron-builder --publish always` (with a `GH_TOKEN`) uploads them to the GitHub releases, where installed copies find updates. On Linux, `npm run dist:flatpak` (after `npm run dist`; needs `flatpak`, `flatpak-builder` and the flathub remote) also wraps that build in a Flatpak bundle, `release/Multicord-<version>-x86_64.flatpak` (see Linux packages below). Installed copies check for updates at start and every six hours, download them in the background and install them on restart (Settings > About also checks on request); runs from source and Flatpaks never update themselves. Pushing a version tag (`v1.2.3`) runs `.github/workflows/release.yml`, which checks, builds and publishes for Windows, macOS and Linux (the AppImage and the Flatpak bundle); it signs when the repository has the signing secrets listed at its top (a Windows code-signing certificate; a macOS Developer ID certificate and Apple ID for notarization), and builds unsigned otherwise. Getting those certificates is up to the owner. `.github/workflows/ci.yml` runs the checks on every push and pull request on all three systems. The app icon is drawn in `assets/icon.svg` (two chat bubbles: the service in front and another behind) and rendered by `npm run icons`.

**Linux packages.** The AppImage runs unconfined, like any program you start. The Flatpak (`io.github.sverredraaisma.Multicord`, manifest in `build/flatpak/`) runs the same build in Flatpak's sandbox on `org.freedesktop.Platform` 26.08 with the Electron BaseApp; install it with `flatpak install --user Multicord-<version>-x86_64.flatpak` (the runtime comes from flathub), and install a newer bundle the same way to update. It has these permissions and no access to your home folder:
- `--socket=wayland`, `--socket=fallback-x11`, `--share=ipc`: the window, natively on Wayland, through X11 only where there is no Wayland.
- `--device=all`: the GPU and cameras. Chromium opens `/dev/video*` itself, and Flatpak has no narrower permission that covers cameras.
- `--socket=pulseaudio`: speakers and microphone.
- `--filesystem=xdg-run/pipewire-0`: the PipeWire socket, for screen-share sound through venmic.
- `--share=network`: the services.
- `--talk-name=org.freedesktop.secrets`, `org.kde.kwalletd5`, `org.kde.kwalletd6`: the keyring that `safeStorage` keeps sign-in secrets under (GNOME Keyring, KeePassXC or KWallet). Without one, Multicord keeps them in memory only, as outside the sandbox.
- `--talk-name=org.freedesktop.Notifications` and `org.kde.StatusNotifierWatcher`: notifications and the tray icon.
- `--env=XCURSOR_PATH=...`: the host's cursor theme under Wayland.

Global shortcuts, screen capture and opening or saving files go through the desktop portals, which need no permission. In the sandbox, Rich Presence listens in `$XDG_RUNTIME_DIR/app/io.github.sverredraaisma.Multicord/` (the host sees that folder, but apps look in `$XDG_RUNTIME_DIR`); to let apps outside reach it, link it once per login, as with Discord's own Flatpak: `ln -sf "$XDG_RUNTIME_DIR/app/io.github.sverredraaisma.Multicord/discord-ipc-0" "$XDG_RUNTIME_DIR/discord-ipc-0"`. What the Flatpak cannot do: detect games or streaming software (it sees only its own processes), open `discord://` links (it cannot register as their handler on the host), or launch at login (not offered on Linux in any package). Push to talk in the background needs X11, so it works only in an X11 session, as outside the sandbox; screen-share sound needs the host to run PipeWire.

## What v0.1 does

- **Platform modules:** every platform is a module with a manifest in `src/main/modules` (id, label, colour, which view it uses, whether users may add instances, and for native modules its engine, hosts and capabilities). The shell knows platforms only through this interface; a new platform is a new module, with no changes to the shell. The built-in modules are `discord`, `fluxer`, `telegram`, `matrix-native` and `stoat-native` (native), and the web-client modules `fluxer-web`, `matrix` (Element), `stoat`, `spacebar`, `nerimity`, `mumble` and `web`.
  [docs/modules.md](docs/modules.md) explains how to add a module, with a template and a checklist.
- **Isolated module engines:** a native module's logic (Fluxer, Telegram, Matrix, Stoat) does not run in the main process. It runs in an *engine*: a hidden renderer with Chromium's sandbox, no Node, its own session (in memory, or on disk for modules that keep encryption keys, separate per instance and cleared when the instance is removed), and a page on its own origin (`multicord-engine://<module>`) with a strict CSP. The engine reaches the shell only through a bridge the main process validates and binds to that one engine:
  - its own secrets (stored encrypted with `safeStorage`, under its instance id; it cannot name another instance's keys),
  - HTTP through the main process with the engine's own cookie-less session: https only, never local or private addresses, only the module's declared hosts if it declares any (an engine may lock itself to its instance's hosts once it has discovered them, and a lock can only narrow. Stoat and Matrix do this. Fluxer doesn't, since its presigned uploads go to storage hosts it cannot know in advance), each redirect checked again,
  - WebSockets only to the same allowed hosts,
  - files only through handles for what the user picked for it,
  - single sign-on (Matrix's `m.login.sso`) only right after the user submits a sign-in step in the module's own view: the shell opens the homeserver's SSO address (on a host the engine may reach) in the browser, receives the one login token that comes back on a random loopback address (127.0.0.1 only, one request, five minutes at most), and hands it to that engine alone,
  - display state only to its own view, and that view's actions only back to it.

  A module therefore cannot read another module's tokens, cookies, storage or messages. Code under `src/modules` and `src/engine` may not import Electron, Node or main-process code; a test enforces it. Web-view modules (Discord, generic web apps) run their pages in their own sandboxed, partitioned views, with only narrow preload bridges.

  A crashed engine restarts after 2 seconds, then with doubling delays up to 30 seconds. After five crashes in a row it stays stopped. Settings > Diagnostics shows whether each engine is running and responsive, and how often it has restarted, followed by the module's own checks of its service where it makes some.
- **Your own server order:** servers and folders from every platform form one list in the rail. Drag them into any order; the order is saved in `rail-order.json`, and new servers join at the end. Each platform's Home and DM bubbles stay at the top.
- **Module labels:** hovering a rail icon shows a small dot in its module's colour with the module's initial (D, F, W) in the corner, and the hover name says it too, e.g. "Alpha · Fluxer".
- **Unified Messages:** the button at the top of the rail lists the direct messages of every service in one list, most recently active first, with the last message where the service provides it (Fluxer, Telegram, Matrix and Stoat do; Discord does once its client has that message loaded, and not while Discord's own streamer mode is on) and a search box. Picking one opens it beside the list in its own service; the services hide their own DM sidebars meanwhile. The button shows the unread DM count.
- **Settings** (the gear at the bottom of the rail, or the tray menu):
  - **Services and accounts:** turn services on and off, rename them, turn notifications off per service (for native and web services alike; the general switch still rules), add web apps, self-hosted Fluxer instances and extra Discord or Fluxer accounts (each account is its own service, with its own session), remove added ones (which also deletes their saved sign-in), and see who is signed in. Sign out of each service from here too. Service changes are written to `platforms.json` and apply after a restart, which the page offers.
  - **Per-service settings:** each service's own settings show under it, declared by its module and seen only by that service: for Matrix, whether others see you typing and which call services Multicord remembers (with a button to forget them); for Telegram, which API ID is in use and a button to forget one you entered.
  - **Voice and video:** microphone, speakers and camera, with a level meter, a test sound and a camera preview, plus echo cancellation, noise suppression and automatic gain control, and optional enhanced noise suppression with RNNoise (the open stand-in for Krisp, run in an AudioWorklet). These apply to calls in the native views (Fluxer, Matrix, Stoat); Discord and web apps keep their own voice settings.
  - **General:** keep running in the tray, start with your computer (Windows and macOS), desktop notifications, spell check, grouping servers by service in the rail (the study's open question, now a choice; one mixed list in your own order by default), zoom for the content area (also Ctrl and +, − or 0), opening `discord://` links in Multicord (off by default, since an installed Discord app may want them; modules declare the link schemes they open), and streamer mode: automatic while OBS or other streaming software runs (the study's auto-detect), always, or off. It keeps message content out of notifications and the Messages list.
  - **Rich Presence** (General, off by default): a local server speaking Discord's IPC protocol, as arRPC does, on the first free `discord-ipc-0` to `-9`, so games show "Playing …" on your Discord account. Activities are cut down to the fields Discord shows (text trimmed, only uploaded image names, at most two https buttons). The app's name and images come from Discord's public application endpoints. Discord's page then publishes the activity through its own `LOCAL_ACTIVITY_UPDATE`, the one action Multicord dispatches in Discord. Any program on the computer can set the status, as with the desktop app. It also detects games the way the desktop app does. Every 15 seconds it checks running processes against Discord's public list of detectable games, downloaded once a day. The first game found shows as "Playing …" until it closes, unless the game reports its own Rich Presence.
  - **Auto-load media** (General, 5 MB by default; Off, 1, 5, 10 or 25 MB, or Any size): pictures, video and sound that Matrix and Telegram fetch on request load by themselves when the service says how large they are and they are no larger than this. Larger ones, and those whose size the service does not say, show a button instead, whose tooltip says why; "Any size" loads those too. Stickers always load, as every platform keeps them small, and other files load when you click them. Media is asked for once it scrolls into sight, at most three at a time; one the engine could not load is not tried again by itself. Matrix and Telegram services can each choose their own limit under Services & accounts, or follow the general one. The shell sends each view only its own service's limit; engines never see settings. Fluxer and Stoat show media straight from their own servers, so the limit does not apply there: pictures load as they scroll into sight and videos only fetch their first bytes until played.
  - **Voice > Keybinds:** system-wide shortcuts for toggling mute, toggling deafen and showing or hiding Multicord. They need a modifier, or F13 to F24 alone, and a shortcut another app already holds is flagged. Mute and deafen act on Fluxer calls and send Discord its own Ctrl+Shift+M and Ctrl+Shift+D. A push-to-talk key works in Fluxer calls. With "Push to talk in the background" on, it works while Multicord is not in front too. A keyboard hook (uiohook-napi) is loaded only then, and only presses and releases of that one key leave it. The key is also passed on to Discord, whose own push to talk then works in the background (set the same key there). macOS asks for the Accessibility permission. On Linux, global shortcuts go through the desktop portal so they work under Wayland; the background push-to-talk hook needs X11.

  - **Favourites:** how many favourites there are, their categories with how many each holds, and how much space the cached files take, with "Clear cache" (a second click confirms). Clearing keeps the favourites; their files are downloaded again the next time they are shown or sent. Files saved from media a service loaded itself (Matrix, Telegram) have no address to download again, so clearing keeps them.

  Settings are stored in `settings.json` in the user-data folder.
- **Markdown and emoji:** messages render Discord-flavoured Markdown (headings, emphasis, spoilers, code, quotes, lists, links) and custom emoji. `:shortcodes:` become emoji, and emoji-only messages show large. An emoji picker with search, groups and the server's custom emoji sits in the composer and on reactions.
- One `BaseWindow` with a shell rail view and one `WebContentsView` per platform, each in its own `persist:<id>` partition, with `contextIsolation` and `sandbox` on.
- **Discord, hidden engine:** loads discord.com, hides its guild bar with CSS and reads the hidden guild items to build our rail, keeping their order and unread state. Server names and icons come from Discord's `GuildStore` through the store bridge, with DOM fallbacks. Navigation clicks the hidden items so Discord's own router handles it, with `pushState` + `popstate` as a fallback. It never calls `loadURL()`.
- **DMs in the rail:** a Home entry plus unread DM bubbles (avatar and mention count, newest first, up to 10; mentions from any extra DMs are added to the Home badge). A small script in Discord's page (`storeBridge.ts`) reads its channel, read-state and user stores, and the last message of each DM from `MessageStore` (only messages the client already loaded; nothing is fetched) as a one-line plain-text preview, with mentions resolved, Markdown dropped, spoilers hidden and the author named in group DMs. It only reads them, and its output is validated in the preload and again in the main process (previews at most 200 characters, without control or bidirectional characters). All DMs also feed the unified Messages list.
- **One notification path:** Discord's notifications are relayed from its page (a small script replaces the page's `Notification` constructor, a browser API, not Discord internals) and shown by Multicord like every other platform's, so the notification switch and streamer mode apply to them too. Clicking one runs Discord's own click handler, so Discord navigates itself.
- **Incoming calls:** when someone calls you on Discord while another view is in front (where Discord's own ringing is hidden), Multicord rings itself: an urgent notification that stays until handled, and a taskbar flash. Clicking it opens the call's DM in Discord. The store bridge reads ringing calls from Discord's `CallStore`; adapters report calls through the same contract, so other platforms can ring the same way.
- **Server folders:** a collapsed folder is a tile in the folder's colour that previews up to four of its servers and shows their combined badge. An expanded folder groups its servers in one tinted container under a folder icon. Clicking a folder clicks Discord's own hidden folder header, so Discord keeps track of which folders are open. Folder structure comes from `SortedGuildStore`, which also covers servers inside collapsed folders. Without it, folders are detected from the DOM.
- **Hover names:** hovering any rail item shows its name in a tooltip. The rail view is only 72px wide, so the tooltip is drawn in a transparent overlay view beside it.
- **Media in the native views:** attachments say what they are, and the native chat view shows pictures inline at their real size, videos and sound with players, GIFs and video stickers looping silently, stickers small and other files as links. Media an engine has to fetch itself (Telegram, Matrix's authenticated and encrypted media) reaches the view as a `data:` URL, at most 40 MB a file and 200 MB kept per service. It loads by itself up to a size you choose (see Auto-load media below), and otherwise when you click it. Fluxer also shows its stickers and links that are pictures, GIFs or videos; Matrix checks encrypted attachments against their hash before decrypting them.
- **Emoji, stickers, GIFs and favourites in the native views:** the composer's picker (the smiley button) has four tabs, Emoji, Stickers, GIFs and Favourites, with a search box, and works from the keyboard (arrow keys between tabs and items, Escape to close). Everything in it shows where it comes from: the module's badge in its colour with the server or pack name, or "Your favourites" with the badge of the platform it was saved from. It offers only what can be used in the open conversation: Unicode emoji always, custom emoji and stickers as each module allows them there, and favourites only where files may be sent.
  - **Favourites:** a star on any picture, GIF, looping video or sticker in a message (on hover or keyboard focus), or on a sticker or GIF in the picker, keeps it. Favourites live in the shell, never in a module: an index (`favourites.json`) and one file per favourite in the user-data folder's `favourites` folder, named by the SHA-256 of its bytes, so they show at once without waiting for their platform. Files are downloaded once through a session of the shell's own (https only, public addresses only, within the module's hosts, an image or MP4/WebM type, at most 20 MB, and checked by their first bytes: PNG, APNG, JPEG, GIF, WebP, AVIF, MP4 and WebM, never SVG), or taken from the bytes the view already has. The native views load them as `multicord-media://media/<id>`, which only they can reach; no engine can. At most 2000 favourites.
  - **Categories:** make, rename, reorder and delete categories in the Favourites tab ("Edit categories"), and put a favourite in any number of them from its menu (the ⋯ button), where it can also be removed. Deleting a category keeps its favourites.
  - **Stickers that cannot go as stickers:** a module sends its own stickers natively where the conversation allows it. Elsewhere (a favourite sticker from another platform, or a conversation where you may not send stickers but may send files) the sticker goes as a file, by format: static PNG, WebP and AVIF as the picture; APNG, GIF and animated WebP as the animated picture, unchanged; WebM video stickers as a WebM video (not converted to a GIF, which would be large and slow to make); Lottie (Telegram's TGS) as its still picture, since drawing Lottie needs a renderer Multicord does not ship. In messages, WebM stickers loop silently and Lottie stickers show their still, labelled "Animated sticker". Telegram lists its stickers only where they can go as stickers, so its chats' rules on stickers are not got round.
  - **GIF search** appears where the platform offers one without a key of Multicord's own: Fluxer (its own /gifs search). Elsewhere the GIF tab shows your favourite GIFs and GIFs seen in the conversation.
  - **Sending a favourite** (or a GIF seen in the conversation) uploads it as a file through the module's normal attach path; it goes at once, or with files already waiting. The module gets the file through a handle, as with files you pick, and never reads the favourites themselves.
- **Members and profiles in the native views:** where a service lists a conversation's members (Telegram groups; Fluxer and Stoat channels, DMs and groups; Matrix rooms), a button in the conversation header opens a member panel beside the conversation (over it in narrow windows): sections such as "Admins" and "Members", each person with their picture, presence and status, at most 200 at once with "N more" for the rest and "Load more" for further pages. Clicking a member, or a message's author, opens a small profile card with what the service shows other users.
- **Mentions in the native views:** messages that mention you are highlighted with a bar, a tint and an "@" marker (read out as "Mentions you"). Typing `@` and the start of a name in the composer lists the people who wrote recently in the conversation, and its members while the member panel lists them; arrow keys move through the list, Enter or Tab inserts the mention and Escape closes it. What goes in is the service's own mention where the module gives one, and otherwise the name.
- **Link previews in the native views:** previews the service made for a link (site, title, description, picture) show as cards under the message; the title opens the link in your browser. Multicord never fetches a linked page itself to make one, so the site does not learn who read the message. Pictures held back by the module load like other media.
- **Pinned messages in the native views:** pinned messages carry a pin. Where the service lists them, a pin button in the conversation header opens a panel of them beside the conversation (newest pin first); clicking one scrolls to it and marks it, loading older messages as needed (up to twenty pages), or says when it cannot be reached. Where you may pin, a message's menu offers "Pin" or "Unpin"; the service decides, and says so when it refuses.
- **Replies in the native views:** a reply quotes the message it answers (its author and text) above itself. Where the module says which message that is (Stoat), clicking the quote scrolls to the original and marks it, loading older messages as needed like a pinned message, or says when it cannot be reached.
- **Search in the native views:** where the service can search a conversation, a magnifier in its header opens a search field beside it; results (newest first) open like pinned messages, scrolling to the message and loading older ones as needed. The search runs on the service's servers, so what it finds is up to them; closing the panel or opening another conversation ends it.
- **Forwarding and copying in the native views:** where the service can, a message's menu offers "Forward", listing the other conversations of the same service in the sidebar; the module forwards natively where the service has forwarding, and otherwise sends it as a new message saying who wrote it. Forwarding never crosses services: one service's module never sees another's messages. "Copy text" puts a message's text on the clipboard, to take it anywhere.
- **Polls in the native views:** polls show their question and options, with each option's share of the votes where the service shows it. Where you may vote, clicking an option votes for it (or, in a poll with more than one answer, adds or removes it), and "Take back vote" withdraws it.
- **Unread messages in the native views:** opening a conversation with news shows a "N new messages" divider where it starts and scrolls there. While that point is out of sight above (or not loaded yet), a bar offers "Jump to unread", loading older messages as needed (up to ten pages); it goes away once dismissed or once you have read on to the latest messages. Scrolled up more than a screen, "Jump to present" takes you back down.
- **Threads in the native views:** where a service keeps threads under a message (Matrix), the message shows "N replies" with who wrote the latest, and opening it (or "Thread" in its menu) shows the thread in a panel beside the conversation, with a composer that replies in the thread. Services whose threads are conversations of their own (Fluxer) list them in the sidebar.
- **Invitations and joining in the native views:** where the service has them, invitations show in the sidebar with who sent them and Accept and Decline buttons, and conversations you may join (such as a space's rooms) with a Join button. Where the service can join by address, a field under the sidebar takes one.
- **Folding sidebar sections in the native views:** sections a service marks as foldable fold away with a click on their heading, showing their unread state and mentions while folded; the open conversation stays in sight. The view remembers the choice while it is open.
- **Folders in the native views:** where a service has folders of your own (Telegram's chat folders), they show as tabs above the sidebar with their unread state and mentions; picking one shows only its conversations.
- **Calls in the native views:** where a conversation takes calls of its own (a DM, or a channel that is also a voice channel), a call button in its header starts or joins its call. A call ringing for you shows above the conversation with who is calling and Accept and Decline buttons, and as a notification while Multicord is not in front.
- **Muted conversations in the native views:** conversations muted on their service show dimmed with a crossed-out bell (read out as "Muted"). Where the service lets Multicord change it, a bell beside the conversation (on hover or keyboard focus) mutes or unmutes it on the service itself. Where the service has an archive, a button beside it moves it into the archive or out again.
- **Fluxer, native:** a built-in Fluxer client. Multicord talks to Fluxer's API itself and shows the chat in its own view, instead of embedding Fluxer's web app. It covers:
  - signing in, including Fluxer's proof-of-work captcha, authenticator codes and backup codes
  - the server list with folders, unread badges and mentions, in the shared rail
  - DM bubbles
  - channel lists, message history, sending messages and marking channels read
  - replies, reactions (with quick reactions), and editing and deleting your own messages
  - typing indicators
  - where the news begins: opening a channel with unread messages marks the first after your read position (Fluxer gives no count, so the divider says "New messages")
  - mentions: messages that mention you, a role you have in that server or @everyone are highlighted (role mentions show the role's name, and notify unless you turned role mentions off for that server in Fluxer), and `@name` in the composer inserts a real Fluxer mention of someone who wrote recently
  - attachment uploads, picked with the OS file dialog
  - link previews Fluxer made (articles, site cards, bots' rich embeds) as cards, their pictures through the instance's media proxy
  - pinned messages: a channel's pins in the pins panel (its latest 100, fetched in pages), followed live, and pinning or unpinning from a message's menu (Fluxer decides who may; Multicord does not work out permissions, so it offers it on every ordinary message and shows Fluxer's refusal)
  - search in the open channel or DM, on the instance (its first 25 results, newest first); the instance says when it is still indexing
  - forwarding a message natively (Fluxer's forward, which copies it without naming its author) into another channel or DM listed in the sidebar; forwarded messages show their copy quoted under "Forwarded"
  - custom emoji, stickers and GIFs in the picker, by Fluxer's rules: a server's own emoji and stickers there, and every server's (also in DMs) only for accounts with global expressions, which Fluxer gives premium (Plutonium) accounts or whomever the instance's limits say. Stickers are WebP, still or animated, and go as stickers; Lottie stickers in messages show their name. GIF search uses the instance's own provider (Klipy on fluxer.app), with trending GIFs before you type, where the instance has one
  - member lists for text channels and DMs: a channel's list as Fluxer groups it (hoisted roles, then online, then offline), with presence, custom status and role colours, asked for over the gateway only while the panel is open, 100 at a time up to 200, with the rest counted. Profile cards show a user's name (their nickname on the server), tag, pronouns, bio and roles on the open server; members picked from the list are mentioned as real Fluxer mentions
  - threads under their channel, and forum channels with their posts and a form for new ones
  - voice channels with who is in them, and calls with microphone, camera and screen share (through LiveKit, as Fluxer uses)
  - calls in DMs and groups: the call button in the header starts one, which rings the others, or joins the one going on; a call ringing for you shows above the conversation with Accept and Decline (which stops it ringing for you, as in Fluxer's apps) and as a notification while Multicord is not in front; who is in a call shows under its DM
  - desktop notifications that follow your Fluxer notification settings (mutes, server and channel levels, @everyone suppression); muted channels and DMs show as muted, and the bell beside a channel, DM or group mutes or unmutes it in those settings for good (not threads, which Fluxer mutes per thread, nor where the whole server or all DMs are muted, which a channel's own mute cannot undo)
  - service status in Settings > Diagnostics: whether the instance's API, gateway and media servers answer their documented health checks (`/_health`), asked every five minutes, with the instance's status page where it names one

  Large servers (over 250 members) are subscribed to while open, so they deliver every message.

  The client runs in its sandboxed engine; the session token is stored encrypted and never reaches a web page. Multicord identifies itself to Fluxer honestly, as Multicord. Self-hosted instances and extra accounts can be added in Settings or in `platforms.json` with `"module": "fluxer"` and the instance URL.
- **Telegram, native:** a built-in Telegram client over MTProto (GramJS) from its engine, which may only reach Telegram's web endpoints (`*.web.telegram.org`). It covers:
  - signing in with phone number, code and two-step password;
  - one-to-one chats (with people, bots, and yourself as "Saved Messages") with unread counts and profile pictures, as DM bubbles and in the unified Messages page with previews;
  - basic groups, supergroups and broadcast channels under the Telegram home entry, whose sidebar lists "Direct messages", "Groups" and "Channels", and archived chats of every kind under "Archive", which starts folded as in Telegram's apps. The archive button beside a chat moves it into the archive or out again (Saved Messages stays out), and chats Telegram moves (such as an archived chat that gets news) follow. As with Matrix rooms, groups stay out of the DM bubbles and the Messages page: Telegram groups can be large and public, unlike the small group DMs of Fluxer and Stoat. Group messages name their sender. A group counts only unread mentions and answers to you, which the home entry adds up; channels you cannot post in, and groups you may not write in, are read-only;
  - history, sending, replying, and editing and deleting your own messages, with deletions in supergroups and channels followed live;
  - formatting both ways: Telegram's bold, italic, underline, strikethrough, spoilers, code, code blocks, text links and quotes show as the view's markdown, with every other `*`, `_` and the like shown literally, and what you type in markdown is sent as Telegram formatting, so a message reads the same before and after it is sent. Headings and lists, which Telegram lacks, go as the text you typed; mentions, hashtags and custom emoji show as plain text. Where markers could not show overlapping styles faithfully (italic pressed against bold inside a word), the message shows unstyled rather than wrong;
  - link previews Telegram made for a message's link (site, title, description) as cards, the page's photo loading like other media;
  - pinned messages: a chat's pins (up to 50, newest first) in the pins panel, followed live, and pinning or unpinning from a message's menu, quietly as Telegram's apps can; in groups Telegram decides who may. Forum groups' pins are not listed;
  - search in the open chat with Telegram's own search (its newest 50 matches); forum groups are not searched yet;
  - forwarding a message natively (as Telegram's apps do, naming where it came from) into another chat or a forum's topic listed in the sidebar; Telegram refuses where a chat protects its content;
  - polls and quizzes: the question and answers with their share of the votes as far as Telegram shows them (usually once you have voted), followed live, and voting, changing or taking back your vote from the view;
  - emoji reactions with their counts, followed live, given and taken back from the view: one per message, or three with Telegram Premium, a new one replacing the oldest as in Telegram's apps. Only reactions a chat takes are given (groups and channels may allow some or none, which hides the control), and only those Telegram offers you. Reactions with custom emoji and paid ones are not shown, as showing them would mean fetching their stickers;
  - typing notices both ways: who is typing (or sending a photo, recording and the like) shows by name for six seconds unless they go on, as in Telegram's apps, and ends when their message arrives; your own typing is sent at most every five seconds and called off when you send;
  - sending files: up to ten per message, each sent as a message of its own (JPEG and PNG pictures up to 10 MB as photos, videos as videos, everything else as files), with your text as the last one's caption, or after them when it is longer than a caption may be (1024 characters, 4096 with Premium). Files go up to 50 MB, the most the engine's bridge carries for any module (Telegram itself takes 2 GB), uploaded in parts as they are read. Groups that bar you from sending media offer no attach button;
  - sticker sets in the composer's picker: your favourite and recent stickers, then your installed sets (up to 100, fetched when you first open the picker), sent as real Telegram stickers, as replies and into forum topics too. Static stickers show as their WebP, video stickers as their looping WebM, and animated (TGS) stickers as their still thumbnail, labelled as such; the same goes for stickers in messages. Stickers are offered only where you may send them: not in read-only chats, nor in groups that bar you from stickers or media. Premium stickers are left out unless you have Telegram Premium. The pictures load only while the picker is open and go to the view only then; they are kept within 24 MB, so with very many sets the last stickers are not offered. Custom emoji are not offered, as Multicord cannot yet send them as Telegram's custom emoji, and Telegram's GIF search (an inline bot) is not offered either;
  - forum groups (supergroups with topics): opening one lists its topics, pinned first and then the most recently active, up to 50, with their unread counts and mentions, both as the conversation's post list and as threads under the group in the sidebar. A topic opens with its own history, read on its own; messages, replies, files and typing go into the open topic, and messages arriving in other topics count as unread there. New topics can be started from the post list, with their first message, where the group lets members start them;
  - mentions: messages that mention you or answer yours (as Telegram flags them) are highlighted, and `@name` in the composer inserts `@username` for people who have one, which Telegram makes a mention; others go in by name, as plain text;
  - where the news begins: opening a chat or topic with unread messages marks the first incoming one after the last you read, as Telegram records it;
  - member lists for groups and for channels you administer: admins first, then members, those online first, with "last seen recently" where that is all a user shows. Large groups list their admins and most recent members, up to 200, and count the rest; groups that hide their members from all but admins offer no list. Profile cards show a user's name, username, bio and role, never their phone number;
  - notifications that follow each chat's mute in Telegram: a muted chat stays quiet, except for a mention or an answer in a group, and a muted one-to-one chat shows as unread without a count. Telegram's defaults for all chats of a kind (Settings > Notifications) are not read yet, so a chat muted only that way still notifies. The bell beside a chat in the sidebar mutes it in Telegram for good, or unmutes it, as Telegram's apps do; topics follow their group.

  Photos, videos, GIFs, voice messages and audio, stickers (animated ones as their still picture) and files show in the chat, downloaded by the engine when they come into view or, for sound, video and files, when clicked; files over 40 MB say to open them in Telegram. Locations, contacts and polls show as a short label. Up to 1000 chats are listed: the 100 most recent (with pinned chats) at sign-in, then the next 100 every two seconds in the background. There is no local Telegram server to test against, so the module is covered by unit tests with a fake of GramJS, not by a live suite.
- **Stoat, native:** a built-in client for Stoat (formerly Revolt). It talks to the instance's API and events WebSocket from its sandboxed engine. You sign in with email and password, then an authenticator or recovery code. It covers:
  - servers in the rail with icons, unread state and mentions;
  - DMs and groups as DM bubbles and in the Messages page, with previews;
  - your own notes (Stoat's saved messages) as "Saved Notes" at the top of the home sidebar, also as somewhere to forward to. Stoat makes the channel the first time it is opened or forwarded to;
  - channel history, sending, replies, reactions, and editing and deleting your own messages. A reply quotes the message it answers, fetched from the instance when it is not loaded (the latest ten per page), and clicking the quote goes to it;
  - typing indicators, read state, and attachments uploaded to the instance's file server;
  - link previews the instance made (sites, linked pictures, bots' text embeds) as cards; a site's picture loads only through the instance's own proxy (January), which joins the hosts the engine may reach, and is left out where there is none;
  - pinned messages: a channel's pins in the pins panel (found with Stoat's search), followed live, and pinning or unpinning from a message's menu, which Stoat allows or refuses;
  - search in the open channel on the instance (its newest 100 matches; Stoat takes the first 64 characters of a search);
  - member lists: a server's members (Stoat sends the whole list, fetched only when the panel opens and then kept current by member events), online ones under their highest hoisted role or "Online", then "Offline", with role colours and status texts, up to 200 shown and the rest counted; DMs and groups list their people. Profile cards add a user's tag, their nickname and roles in the open server and what they wrote about themselves;
  - forwarding a message into another channel, DM or group listed in the sidebar: Stoat has no forwarding, so a new message says "Forwarded from" its author and quotes the text, with links to its files; mentions in it are made plain text, so the copy pings nobody;
  - where the news begins: opening a channel with unread messages marks the first after your read position (Stoat gives no count, so the divider says "New messages");
  - mentions: messages that mention you, a role you have in that server, everyone or everyone online are highlighted (role mentions show the role's name), and `@name` in the composer inserts a real Stoat mention of someone who wrote recently;
  - custom emoji from your servers in the emoji picker, for messages and reactions. A server channel offers its own server's emoji, since another server's need a permission there that Multicord does not work out; DMs and groups offer every server's. Messages and reactions show custom emoji with their picture (by name where the instance has no file server). Stoat has no stickers, and its GIF search (Gifbox) needs a key of its own, so neither is offered;
  - calls in server channels that are also voice channels, with microphone, camera and screen share: the call button in the channel's header asks Stoat for a grant on one of the instance's voice servers (LiveKit, through its documented `join_call`), whose hosts join those the engine may reach. Who else is in a call is not shown, and calls in DMs and groups and the voice-only channels of older instances are not offered, as Stoat does not document the events and steps they need;
  - notifications that follow your Stoat notification settings. Channels, DMs and groups muted there (or in a muted server) show as muted, and the bell beside one mutes or unmutes it in those settings, which Stoat's own apps share.

  Self-hosted instances can be added with `"module": "stoat-native"` and the instance URL. The web client stays available as "Stoat (web)".
- **Matrix, native:** a built-in Matrix client for any homeserver; matrix.org is the default, and Element stays available as a web view. It talks to the homeserver's API directly from its engine, with no SDK. There are four ways to sign in:
  - **Your homeserver's account page, in the browser** (OAuth 2.0 with a code you confirm). matrix.org and other homeservers that run the Matrix Authentication Service give Multicord a device of its own this way, and your password never passes through Multicord.
  - **Single sign-on, in the browser** (`m.login.sso`), where the homeserver offers it: its sign-in page (or the identity provider it sends you to) opens in your browser and sends the browser back to a one-time address on this computer (127.0.0.1, a random port and path) with a login token, which Multicord exchanges for a device of its own (`m.login.token`). The shell receives the token, not the engine, and only for the sign-in you just started; see the engines bullet above. Your password never passes through Multicord.
  - **A password**, where the homeserver offers password sign-in.
  - **An access token copied from Element.**

  It covers:
  - direct chats as DM bubbles and in the unified Messages page, with previews, unread counts and profile pictures, plus your other rooms in its sidebar;
  - spaces as servers in the rail: each top-level space you have joined gets an entry with its picture and unread/mention badge, and opening it lists its rooms, with each subspace's rooms under the subspace's name. Only rooms you have joined are listed; direct messages, and rooms in no space, stay under Home;
  - invitations: rooms, spaces and direct chats you are invited to show at home under "Invitations", with who invited you, a notification for each new one, and Accept and Decline. Their pictures are not fetched, as an invitation can come from anyone. An accepted direct chat is added to your direct chats (`m.direct`), as Element does. A field under the sidebar joins a room by its alias (`#room:server`), its ID or a matrix.to link (through the servers the link names); a room already joined opens instead. Opening a space lists its rooms you have not joined under "Not joined" (from the space's hierarchy, one level down, fetched once per session), to join through the servers the space names;
  - history, sending, replying, and editing and deleting your own messages;
  - threads (`m.thread`): replies stay out of the room's timeline, and their root shows "N replies" with who wrote the latest, counted by the homeserver (its bundled summary) or from the replies Multicord has, whichever is more. Opening it shows the root and its latest 50 replies (fetched from the homeserver, decrypted where they can be) beside the room, with a composer that replies in the thread as the spec says: the thread relation, and the thread's latest message as the fallback reply for apps without threads. Replying to one particular message inside a thread is not offered, and the replies listed are not edited or reacted to from the thread panel;
  - formatting: bold, italics, underline, strikethrough, spoilers, code, code blocks, quotes, lists, headings and links from other apps show formatted. Their HTML is hostile input, so the engine reads it into the view's markdown (checked by parsing it back) and the view never gets HTML; links are kept only when they are https, the reply fallback (`mx-reply`) and pictures other than custom emoji are dropped, and formatting that cannot be shown as meant shows as the plain text. Markdown typed in the composer goes out as HTML for other apps (`formatted_body`, every piece of text escaped), with the text as typed as the plain body;
  - reactions, typing indicators, files and pictures (one message per file, up to the homeserver's upload limit and at most 50 MB);
  - pinned messages (`m.room.pinned_events`): pinned messages are marked, the pins panel lists the newest 50 (fetching and decrypting those not loaded), and a message's menu pins or unpins it in the room's state, which the homeserver allows only with the power to change it;
  - search in the open room on the homeserver (its newest 50 matches). The homeserver cannot read encrypted messages, so in an encrypted room it finds only those sent before encryption was turned on, and the results say so;
  - member lists: the open room's joined members, fetched only while the panel shows them, as "Admins", "Moderators" and "Members" by power level, up to 200 with the rest counted, and pictures of the first 30 through authenticated media. Members picked in the composer's @ list are mentioned by user ID, which goes out as a pill. Profile cards show the name in the room, the user ID, the role, and the user's presence where the homeserver shares it (many turn presence off; the list itself shows none, as Multicord asks sync for no presence);
  - forwarding a message into another room listed in the sidebar, as Matrix has no forwarding of its own: a plain-text copy saying who wrote it, quoting the text and naming its files (the files themselves stay behind, so an encrypted file's key never reaches another room), with empty `m.mentions` so it pings nobody;
  - mentions: messages that mention you (by `m.mentions`, `@room`, or from older clients your user ID or display name in the text) are highlighted. `@name` in the composer inserts the user ID of someone who wrote recently; user IDs in a message are sent in `m.mentions` and as pills (links to matrix.to showing the name), as Element sends them;
  - custom emoji and stickers from image packs (MSC2545, as Element, Cinny and FluffyChat make them): the open room's own packs, your personal pack, and the room packs you enabled for every room (from rooms you have joined). The picker offers up to 500 pictures per room. Custom emoji go into messages as `:name:` with the picture for other apps, and most can be used as reactions. Stickers go as Matrix stickers, encrypted in encrypted rooms. Custom emoji in messages and reactions show with their picture once it has loaded, and as `:name:` until then. There is no GIF search, as Matrix has none of its own;
  - polls (MSC3381, in Element's unstable `org.matrix.msc3381.poll.*` form and the stable `m.poll.*` one) in the shared poll card: the question and answers, with each answer's votes as soon as the poll shows them (at once where it is disclosed, else once it ends). Clicking an answer sends a vote in the poll's own form, encrypted in encrypted rooms. Matrix leaves counting to clients, so Multicord counts the votes in the timeline it has loaded (each person's latest vote before the poll ended): votes in older history not loaded yet are missing from the counts, only an end sent by whoever started the poll closes it (not one from a moderator), and encrypted votes whose keys have not arrived are left out. Starting and ending polls is not offered;
  - notifications for DMs and mentions;
  - where the news begins: opening a room with unread messages marks the first of them, from your read receipt under sliding sync, or else by the homeserver's unread count (classic sync sends no receipts here);
  - muting: rooms muted in Element (a push rule of the room's own that does not notify) show as muted, with no notifications or counts, only whether they have news; the bell beside a room mutes or unmutes it the same way, so Element follows.

  **End-to-end encryption.** On devices of its own, Multicord encrypts and decrypts with the Matrix Rust crypto library (WebAssembly) in its engine:
  - it reads and sends in encrypted rooms, and marks messages from devices their owner has not verified;
  - files sent into encrypted rooms are encrypted on the device with a key of their own (AES-CTR, as Element does), and the homeserver only ever stores the ciphertext, without the file's name. Reactions and typing notices go unencrypted, as Element sends them;
  - its keys live in the engine's encrypted, per-instance storage, which is deleted on sign-out;
  - "Verify this device" takes your Element recovery key or security phrase. It imports your cross-signing keys, so your other devices trust this one, and restores the key backup, so older messages can be read. You can also verify by comparing emoji with another of your devices, such as Element: start it with "Verify with another device", or accept a request your other device sends. Afterwards Multicord asks that device for the key backup's key; if none arrives, "Restore older messages" takes your recovery key.

  With an access token, Multicord is using Element's own device, so encrypted rooms stay locked and nothing (no messages, files or reactions) is sent into them.

  **Sync.** Multicord syncs with simplified sliding sync (MSC4186) when your homeserver offers it, as Synapse does by default: the most recent rooms load first, then the rest. Otherwise it uses classic sync. Under sliding sync Multicord counts unread messages itself from your read receipts, since Synapse does not send counts there, so rooms you have muted still show as unread. To always use classic sync, turn off **Fast sync (sliding sync)** under the service in Settings > Services.

  **Calls.** Calls work the way Element Call makes them (MatrixRTC with LiveKit), in the native view with the same controls as Fluxer calls:
  - ongoing calls and who is in them show under Calls, a call can be started in any room, and calls starting in a DM ring;
  - in encrypted rooms, audio and video are end-to-end encrypted with per-device keys exchanged over Olm, as Element Call does, and Multicord never joins an encrypted room's call unencrypted;
  - the engine's host lock includes the call service. The call's media server is learned on the first call and allowed after one restart.

  Encryption, recovery, emoji verification and the call formats are tested against matrix-js-sdk, Element's own library: its client and Multicord's run against the same test homeserver, both ways. Calls work in both of Element's MatrixRTC formats: the call membership state event, and the newer sticky `m.rtc.member` memberships (MSC4143 with MSC4354 sticky events) that Element Call's "Matrix 2.0" mode sends. Multicord reads both, and joins in the newer format when someone in the call uses it and the homeserver has sticky events. It then publishes on the homeserver's own LiveKit server where the homeserver names one, with access from the homeserver (MSC4195) and a hashed LiveKit identity, and encrypts the membership in encrypted rooms. Call media is checked live by `npm run live:media`: the Multicord app, signed in to a local Synapse with LiveKit and lk-jwt-service, called a matrix-js-sdk MatrixRTC client using livekit-client with Element Call's key handling. In both call formats each side heard the other and saw its camera, LiveKit reported every track as end-to-end encrypted (GCM), audio kept playing through key rotations as a third device joined and left, and wrong keys gave silence. Screen sharing in calls was not part of it. Access-token sessions can't make calls.

  Telegram gives API credentials per app (my.telegram.org, "API development tools"). Builds can include them via the `MULTICORD_TELEGRAM_API_ID` and `MULTICORD_TELEGRAM_API_HASH` environment variables; otherwise Multicord asks for an API ID and hash on first sign-in and stores them encrypted.
- **Component gallery:** `npm run gallery` opens `dist/gallery.html`, which shows every component with sample data. Use it to check designs without signing in anywhere.
- **Extra platforms** as web views (shallow tier: one rail icon, unread state from the page title). Settings offers the open-source platforms from the study by name, each with its own label and colour and its public instance prefilled (self-hosted instances take their own address): Fluxer's own web client (for what the native client refuses: encrypted voice, peer-to-peer calls, security keys), Matrix (through Element web), Stoat, Spacebar and Nerimity, and Mumble through its web client (mumble-web, at your server's address; Mumble's own protocol needs raw sockets no module may open), plus any other web chat app. Settings writes them to `platforms.json` in the app's user-data folder (`%APPDATA%\Multicord` on Windows), which can also be edited by hand:

  ```json
  [
    { "id": "element", "name": "Element", "url": "https://app.element.io" },
    { "id": "work", "name": "Work", "module": "discord" },
    { "id": "fluxer", "enabled": false }
  ]
  ```

  An entry with a built-in id (`discord`, `fluxer`) only renames it or turns it off. Any entry can have `"enabled": false`.

- Tray with minimize-to-tray, single instance, saved window state, and mention counts in the title, badge and taskbar flash.
- Screen share through our own picker, with system audio:
  - on Windows;
  - on macOS 13 and later, where Electron captures it through ScreenCaptureKit, or Apple's CoreAudio tap from 14.2 (untested on a Mac so far);
  - on Linux with PipeWire, through venmic, the helper Vesktop uses: the speakers' sound, minus Multicord's own, goes to a virtual microphone that the sharing page adds to the share.

- Permission allowlist; same-origin popups stay in the app and other links open in the browser.

## Testing policy

Coverage is enforced at **95%** for lines, statements, functions and branches (`vitest.config.mts`). `npm run coverage` fails below that. The only files excluded are the one-line bundle entries and the types-only adapter contract. Keep Electron glue thin and put logic in modules that can be tested.

**Smoke test.** `npm run smoke` (after `npm run build`; `scripts/smoke.mjs`) starts the built app in a scratch Electron with a fresh temporary profile and drives it over the DevTools protocol. It checks that the rail lists the built-in services, that the gear opens Settings on Services & accounts with those services listed, that the Fluxer and Telegram engine pages (`multicord-engine://`) load and are still up seconds later, that no engine crashed, and that the main process logged no uncaught exception or unhandled rejection (caught by a hook loaded through `NODE_OPTIONS`, which Electron honours only for unpackaged apps, so nothing in the app is there for the test). It runs offline: the scratch app resolves no host names but local ones, so the services show their offline or sign-in states (`--online` lets them connect). It stops only its own process tree, deletes the profile (`--keep` leaves it, with its log) and exits non-zero on any failure, printing the log's tail. CI runs it on Linux (under `xvfb-run`), Windows and macOS after the build; it takes about ten seconds.

**Live tests against real servers.** `tests/live/` holds five suites, and `scripts/live-media/` a media check, that `npm run check` and CI skip. Each runs only when its environment variable names a server:
- `matrix.live.test.ts` drives the Matrix module against a real Synapse, with matrix-js-sdk as the other user. It covers sign-in, encrypted DMs, recovery from Element's key backup, emoji verification, encrypted and plain media, reactions, typing and file uploads (encrypted and plain), edits, deletions, read markers, paging, delayed events and sign-out. `MULTICORD_LIVE_MATRIX_SLIDING=1` forces sliding sync and `=0` classic sync; it passes both ways.
- `matrix-calls.live.test.ts` drives Matrix calls against a real Synapse, a LiveKit server and Element's lk-jwt-service, with matrix-js-sdk's MatrixRTC as the other caller. It covers finding the call service, the LiveKit grant (LiveKit itself admits Multicord), call memberships both sides read, the E2EE key exchange both ways, the delayed leave being pushed back, leaving, and a client vanishing mid-call. Sound and video themselves run only in the browser view and are not part of it.
- `matrix-rtc.live.test.ts` drives calls in the newer format against the same servers: Synapse with sticky events and lk-jwt-service as its application service (MSC4195). It covers Element's encrypted sticky membership, joining in that format with a grant from the homeserver under the hashed identity (LiveKit admits it so), media keys both ways under those identities, the delayed sticky leave, leaving, and vanishing mid-call.
- `matrix-oauth.live.test.ts` drives Matrix's browser sign-in against a real Synapse that hands its accounts to the Matrix Authentication Service, as matrix.org does, approving the code on MAS's own pages. It covers finding the account server, registering Multicord, codes that stay pending, are declined, or belong to another app, signing in with a device of its own, refreshing the token before it expires and after the server expired it, resuming, revoking on sign-out, and homeservers whose login endpoint does not reach MAS.
- `npm run live:media` (`scripts/live-media/`) runs a real encrypted call between the Multicord app's own call view and an Element-style peer (matrix-js-sdk MatrixRTC with livekit-client and Element Call's key handling), through Synapse, LiveKit and lk-jwt-service in Docker. In both call formats it checks that LiveKit sees every microphone and camera track end-to-end encrypted (GCM), that each side hears the other's test tone and decodes its video, that sound survives key rotation as a third device joins and leaves, and that wrong keys give silence and decrypt errors. It prints a table, cleans up and exits non-zero on failure. Sound, encryption, rotation and the wrong-key check pass; video failed now and then, traced to Chromium's fake test camera crashing its capture process on Windows, not to Multicord; the runner now starts Chromium with a switch that avoids the crash, not yet confirmed by a full run (see its README). Screen sharing, TURN and mute/deafen are not covered.
- `stoat.live.test.ts` drives the Stoat module against a self-hosted Stoat. It covers sign-in with authenticator and recovery codes, servers, DMs, messages, reactions, typing, read state, mentions, notification settings, attachments, resuming, paging and logout.

Each file's header says how to run it; the servers run in Docker on this machine. All five suites pass. They found two Stoat bugs and five Matrix bugs, since fixed. Call sound and video are checked by `npm run live:media` (see above); its video checks failed now and then because of Chromium's fake camera (see above). Not covered live: opening the sign-in page in the system browser, matrix.org itself, and the Electron shell around the modules.

## Known limitations / next steps
- Spacebar stays a web view. The study suggested trying Multicord's Discord hooks on Spacebar instances, but Spacebar's clients today are its own (the React client and Fermi; the older "legacy" client is Spacebar's too, and unmaintained), not Discord's web app, so those hooks have nothing to attach to. A native Spacebar client on its Discord-compatible API would be a module of its own.
- Rich Presence game detection goes by process name only, so names several games share are skipped. The WebSocket transport some browser-based apps use is not offered.
- Guild selectors (`dom.ts`) and store names (`storeBridge.ts`) follow Discord's current client. Settings > Diagnostics checks them against the running client (each hook, and what breaks if it fails). The running app rechecks every minute: once startup has settled, a check that fails (after working, or at all while signed in) brings one notification pointing there. For repairs, "Copy report" puts the checks, with what each breaks and the versions, on the clipboard, for an issue or an AI assistant to propose a fix. Multicord itself calls no AI service. Guilds could later move to store reads too.
- Linux screen-share sound goes through venmic, which installs on Linux only. Its main-process part was verified on real PipeWire: another app's sound reaches the virtual microphone, Multicord's own does not, and stopping unlinks it. The page side also ran in a Linux Electron (WSLg, PipeWire 1.0.5): the share carried the other app's tone and not the page's own, and ending the share released the microphone. A real "stop sharing" click and Discord's own page were not part of that run. venmic captures sound going to real output devices, not bare virtual sinks.
- Fluxer (native) does not support:
  - **Security keys (WebAuthn):** they are bound to Fluxer's own web origin, and Multicord won't impersonate it. Accounts protected only by a security key can sign in with a backup code.
  - **End-to-end encrypted voice channels:** Fluxer's scheme is undocumented, so Multicord refuses them rather than joining unencrypted.
  - **Peer-to-peer calls:** Fluxer can connect a small call directly between the people in it instead of through a voice server. Multicord never asks for that, so the calls it starts use a voice server, but it cannot join a call that others started peer-to-peer.

  For these, add "Fluxer (web)", Fluxer's own web client, in Settings.
  - **Archived threads:** only open threads and forum posts are listed.
  - **Instances without presigned uploads:** attachments need the presigned upload flow, which fluxer.app supports.
- Fluxer's docs don't state a policy on third-party clients. The client is built to Fluxer's documented API and stays well under its rate limits. Requests are spaced out because a global rate-limit hit revokes a user's session.
